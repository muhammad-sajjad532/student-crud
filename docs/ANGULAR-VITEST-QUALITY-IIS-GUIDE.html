1. Purpose and current status

This project is a small standalone Angular Student CRUD application created to demonstrate a complete and repeatable unit-testing workflow. It uses Vitest to execute tests, V8 to measure code coverage, Allure Report 3 to visualize results, ESLint and Prettier for maintainability checks, GitHub Actions for continuous integration, and IIS for a local Windows deployment.

Verified baseline: 23 of 23 tests pass across two spec files. Statements, branches, functions and lines are all at 100%. Lint, formatting, result gates, Allure generation and the production build pass. The static application is available locally through IIS at http://127.0.0.1:8080.

The student list is intentionally stored in browser memory. Refreshing the page resets it to Ali and Sara. There is no backend API or database in this learning project.

Every push or pull request is checked on a clean GitHub-hosted machine. Dependencies, linting, formatting, tests, coverage, reports and the production build are validated.

Deployment

The application is currently deployed manually to local IIS. GitHub Actions does not connect to or deploy onto the developer's laptop.

3. Application overview

The application exposes one standalone StudentsComponent. It contains a signal-based in-memory list and four public operations.

OperationResponsibilityImportant behavior
saveStudent()Add or update a student.Trims whitespace and rejects an empty name.
editStudent(student)Load a student into the form.Stores the selected ID and clears a previous error.
deleteStudent(id)Remove a student.Resets the form when the edited student is deleted.
cancelEdit()Return the form to add mode.Clears the name, selected ID and error.

The template provides an accessible form, add/save/cancel controls, a student table, edit/delete buttons, a validation alert and an empty state.

5. Vitest and Angular configuration

5.1 Angular test builder

angular.json uses @angular/build:unit-test. Angular compiles TypeScript and templates, initializes its testing environment and loads vitest.config.ts through runnerConfig.

"test": {
  "builder": "@angular/build:unit-test",
  "options": {
    "runnerConfig": "vitest.config.ts",
    "isolate": true
  }
}

Use ng test through the npm scripts. Running raw npx vitest bypasses Angular's builder integration.

6. Unit-testing concepts

6.1 Suite, case, setup and assertion

describe('StudentsComponent', () => {
  beforeEach(() => { /* create a fresh component */ });

  it('should add a student', () => {
    component.name = 'Ahmed';       // Arrange
    component.saveStudent();        // Act
    expect(component.students())    // Assert
      .toHaveLength(3);
  });
});
  • describe: a suite that groups related behavior.
  • it: one independently verifiable behavior.
  • beforeEach: fresh setup before every test.
  • expect: an assertion that decides pass or fail.

6.2 Angular TestBed and fixture

TestBed creates the Angular testing environment. ComponentFixture gives access to both the component instance and its rendered DOM. fixture.whenStable() waits for Angular bindings and events to settle.

6.3 Logic tests and DOM tests

Logic tests call component methods and inspect state. DOM tests type into an input, dispatch an event, click a button and inspect rendered HTML. The DOM is provided by jsdom; this is still a unit/component suite, not a full browser end-to-end test.

6.4 Independence and determinism

Every test creates a new component, uses fixed input data, avoids network calls and does not depend on execution order. This makes local and CI results repeatable.

6.5 Mocking

The current application has no HTTP API, database or external service, so no external dependency requires a mock. When a service is added, use Angular HTTP testing utilities, a fake provider or vi.fn(). Do not add a mock when no dependency exists.

8. Coverage configuration

Coverage uses the V8 provider. Application TypeScript and Angular HTML templates under src/app are included. Specs, interface-only models and framework wiring are excluded.

"coverageThresholds": {
  "perFile": true,
  "statements": 100,
  "branches": 100,
  "functions": 100,
  "lines": 100
}
MetricMeaningCurrent result
StatementsExecutable instructions reached115/115 — 100%
BranchesConditional alternatives reached38/38 — 100%
FunctionsFunctions and handlers invoked16/16 — 100%
LinesExecutable source lines reached72/72 — 100%

perFile: true prevents a well-tested file from hiding another file with poor coverage. Coverage proves execution, not complete correctness; meaningful assertions remain essential.

npm run test:coverage
Start-Process .\coverage\angular-testing\index.html

9. Allure reporting

Vitest decides whether tests pass. Allure presents those results as a browsable report with suites, features, duration, environment and failure details.

Vitest
→
allure-results
→
allure-report
npm test
npm run allure:generate
npm run allure:open

The tests assign the epic Angular application and the features Student management or Application shell. Environment metadata records Node version, platform and whether execution occurred locally or in CI.

Difference: Coverage answers “which code ran?” Allure answers “which test ran, what happened, and how long did it take?” One does not replace the other.

12. GitHub Actions explained

The workflow is stored at .github/workflows/quality.yml. GitHub reads this file after it is pushed to the repository.

12.1 Triggers

on:
  push:
  pull_request:
  workflow_dispatch:

The workflow runs automatically for pushes and pull requests. workflow_dispatch also adds a manual “Run workflow” button.

12.2 Runner and permissions

runs-on: ubuntu-latest creates a fresh temporary Linux machine. contents: read gives the job only the repository read permission it needs. The runner does not use local IIS, local node_modules or the developer's VS Code session.

12.3 Step-by-step execution

StepActionReason
Checkoutactions/checkout@v4Copies repository content onto the runner.
Node setupactions/setup-node@v4Installs Node 24.18.0 and enables npm caching.
Dependenciesnpm ciUses the lockfile for reproducible installation.
Lintnpm run lintRejects code and test-rule violations.
Formattingnpm run format:checkEnforces consistent source formatting.
Test gatesnpm run test:ciRuns tests, coverage and result validation.
Allurenpm run allure:generateProduces a readable report, including after test failures.
Buildnpm run buildRuns only when preceding required checks succeeded.
Artifactsactions/upload-artifact@v4Preserves reports for 14 days on success or failure.

12.4 Failure behavior

A failed test returns a non-zero exit code and marks the job red. The production build is skipped because an earlier required step failed. The workflow still attempts to generate and upload available reports so the failure can be investigated.

13. Reading a CI result

  1. Open the GitHub repository and select Actions.
  2. Select Quality checks and open the latest run.
  3. Open the quality job.
  4. Expand each step to see the exact command and output.
  5. For a failure, begin with the first red step; later skipped steps are usually consequences.
  6. Download test-reports-<run-id>-<attempt> from the Artifacts section.

The artifact contains coverage, Vitest JSON, raw Allure results and the generated Allure report. A displayed SHA-256 value is the artifact's integrity fingerprint, not an error or deployment URL.

Branch protection recommendation: Configure the quality job as a required status check if pull requests must not merge until the pipeline passes.

14. Local IIS deployment

14.1 Why a separate build?

The default production build includes an Angular Node SSR server. IIS is being used here as a static file server, so the iis configuration sets outputMode to static.

npm run build:iis

The deployable files are generated at:

dist\angular-testing-iis\browser

14.2 Enable IIS

Run in Administrator PowerShell:

Enable-WindowsOptionalFeature -Online `
  -FeatureName IIS-WebServerRole,IIS-WebServer,IIS-CommonHttpFeatures,IIS-StaticContent,IIS-DefaultDocument,IIS-ManagementConsole `
  -All -NoRestart

Restart Windows only if the result says RestartNeeded: True.

14.3 Copy the website

New-Item -ItemType Directory -Path "C:\inetpub\student-crud" -Force

Copy-Item `
  -Path ".\dist\angular-testing-iis\browser\*" `
  -Destination "C:\inetpub\student-crud" `
  -Recurse -Force

14.4 Create the IIS application pool and site

& "$env:windir\System32\inetsrv\appcmd.exe" add apppool /name:"StudentCrud"

& "$env:windir\System32\inetsrv\appcmd.exe" set apppool `
  /apppool.name:"StudentCrud" /managedRuntimeVersion:""

& "$env:windir\System32\inetsrv\appcmd.exe" add site `
  /name:"StudentCrud" `
  /bindings:"http/127.0.0.1:8080:" `
  /physicalPath:"C:\inetpub\student-crud"

& "$env:windir\System32\inetsrv\appcmd.exe" set app "StudentCrud/" `
  /applicationPool:"StudentCrud"

14.5 Grant least-required access

icacls "C:\inetpub\student-crud" `
  /grant "IIS AppPool\StudentCrud:(OI)(CI)(RX)" /T

This grants read and execute access to the dedicated application-pool identity. It does not grant write access or broad Everyone permissions.

14.6 Verify deployment

& "$env:windir\System32\inetsrv\appcmd.exe" list site "StudentCrud"
curl.exe -i http://127.0.0.1:8080/

Expected status is state:Started and HTTP/1.1 200 OK. Open http://127.0.0.1:8080 in the browser. VS Code and Node can be closed; IIS and Windows must remain running.

15. IIS troubleshooting

SymptomDiagnosisResolution
applicationHost.config is not well-formed XMLIIS master configuration is corrupted.Validate and restore a known-good configuration-history backup before editing.
Site or pool state is UnknownWAS has not loaded the current configuration.Stop W3SVC/WAS, then start WAS followed by W3SVC.
HTTP 401 despite anonymous authenticationAuthentication module absent, identity wrong, or folder unreadable.Verify modules, use application-pool identity and grant RX permission.
list modules returns nothingIIS configuration lacks standard module registrations.Back up IIS configuration, disable/re-enable the IIS role, then recreate the site.
Connection refused on port 8080No HTTP listener; pool may be Unknown.Restart WAS/W3SVC and confirm netstat -ano | findstr ":8080".
Page loads but refresh loses studentsExpected application design.Add a backend/database later if persistence is required.

Safe configuration recovery

Before restoring or repairing IIS, create a backup. Validate candidate XML before replacement. IIS configuration changes affect every IIS site on the machine.

& "$env:windir\System32\inetsrv\appcmd.exe" list backup

$backupPath = "$env:SystemDrive\inetpub\history\CFGHISTORY_0000000001\applicationHost.config"
$backupXml = New-Object System.Xml.XmlDocument
$backupXml.Load($backupPath)

Reload IIS runtime

Stop-Service W3SVC -ErrorAction Stop
Stop-Service WAS -Force -ErrorAction Stop
Start-Service WAS -ErrorAction Stop
Start-Service W3SVC -ErrorAction Stop

17. Team-lead demonstration

  1. Open http://127.0.0.1:8080 and demonstrate add, edit and delete.
  2. Explain one Arrange–Act–Assert logic test and one DOM test.
  3. Show runnerConfig and the four 100% thresholds in angular.json.
  4. Show the three reporters and safety settings in vitest.config.ts.
  5. Run npm run quality-check and point out 23 tests and coverage.
  6. Run npm run allure:open and show suites, features and duration.
  7. Open the coverage HTML and show file-level coverage.
  8. Open GitHub Actions and explain every workflow step.
  9. Download the workflow artifact and explain the SHA-256 fingerprint.
  10. Clarify that GitHub CI is automated while local IIS publishing is currently manual.
Suggested summary: “Vitest verifies application behavior. V8 measures code execution. Allure visualizes test results. ESLint and Prettier enforce maintainability. GitHub Actions runs the same gates on every push and pull request. A failed test, skipped test, coverage drop or build error makes the quality job fail. The static application is deployed locally on IIS.”

18. Maintenance and next steps

Routine change workflow

  1. Create or update functionality.
  2. Add positive, negative and edge-case tests.
  3. Run npm run quality-check.
  4. Review git diff and git status.
  5. Commit and push.
  6. Verify the GitHub Actions run.
  7. For IIS, run npm run build:iis and copy the new browser files.

Recommended future work

  • Add a Student service and backend persistence, then test HTTP success and failure paths with mocks.
  • Configure branch protection so the quality job is required before merge.
  • Upload the IIS static build as a separate deployment artifact if delivery packaging is required.
  • Use a secured GitHub self-hosted runner only if automatic deployment to this Windows IIS machine becomes a formal requirement.
  • Add end-to-end browser tests when navigation and backend workflows become important.
